# SSH: резервный доступ к VPS

Цель - сохранить административный доступ при отказе прямого пути, не отключив работающий SSH. Нельзя гарантировать отсутствие блокировок IP/протокола, обнаружения трафика или проверок. Смена порта не меняет протокол SSH и не помогает, если недоступен весь IP. WARP - выходной туннель; сам по себе он не создает новый вход SSH.

## Кнопка GoVPN

**8 → a → SSH: резервный доступ** умеет:

- Проверить синтаксис sshd и показать несколько эффективных настроек без их изменения. `sshd -T` без конкретного контекста не учитывает все Match-условия и не проверяет внешний firewall.
- Подготовить SSH config для вашего компьютера: прямой вход и, если указан второй сервер, вход через него с ProxyJump. Адреса, порты и пользователи валидируются как данные. Команды не запускаются, SSH ключи не читаются и не создаются.
- Показать порядок проверки и аварийного восстановления.

Это подготовка плана, а не настроенный или проверенный резерв. Скрипт не меняет sshd_config, authorized_keys, firewall, DNS, порт SSH, а также не устанавливает mesh VPN или внешний агент. Прямой вход сохраняется. Чтобы получить работающий резерв, нужно самостоятельно подготовить второй сервер и проверить оба пути с вашего компьютера.

## Независимый путь

Второй сервер должен оставаться доступен из вашей сети и видеть SSH основного VPS. Желательно уменьшить общие зависимости: другой провайдер/сеть, отдельный адрес и рабочая консоль восстановления. Разная страна сама по себе не гарантирует независимость. Если основной VPS выключен, заблокирован для самого gateway или недоступен из-за firewall, ProxyJump не поможет; нужна консоль/recovery провайдера.

OpenSSH `ProxyJump` сначала подключается к промежуточному SSH-серверу, затем передает SSH соединение к целевому. Проверка host keys остается включенной, ForwardAgent не нужен и выключен в плане GoVPN. Детали: [ssh_config](https://man.openbsd.org/ssh_config), [ssh](https://man.openbsd.org/ssh).

## Порядок без потери входа

1. Проверьте консоль/recovery в кабинете провайдера, восстановление аккаунта и MFA. Это отдельный канал управления.
2. Подготовьте SSH ключ на своем компьютере и защищенную копию. Не переносите приватный ключ на jump host ради ProxyJump. Используйте имеющуюся проверенную учетную запись; отдельный admin user и ограничения root/password планируются отдельно.
3. В GoVPN получите план с реальными адресами/портами. Перенесите блоки в свой `~/.ssh/config`, убедившись, что Host aliases не конфликтуют. Сверьте fingerprints обоих серверов через доверенную консоль и внесите их в known_hosts. Не отключайте StrictHostKeyChecking для удобства.
4. Оставьте текущую SSH-сессию открытой. В двух новых окнах проверьте прямой и резервный вход, права администратора и повторное подключение. При необходимости проверьте резерв из другой сети.
5. Только после этой проверки отдельно меняйте SSH authentication/firewall. Проверка `sshd -t` до reload нужна, но не доказывает, что клиент сможет войти. Консоль провайдера должна оставаться рабочей.

SSH через Amnezia на том же VPS может быть удобным частным доступом, но не единственным аварийным каналом: блокировка адреса или остановка AWG может оборвать и VPN, и вход. Не закрывайте публичный SSH ради еще не проверенной альтернативы. Смена SSH порта на 443 также может конфликтовать с HTTPS/Xray и не превращает SSH в HTTPS.

## Что пока не выполнено

В разработке не создавался второй сервер, не добавлялись SSH ключи, не менялись рабочие VPS и не проверялся реальный внешний вход. Проверены генерация безопасного плана и отказ при SSH-config injection. Для настоящего резервного канала требуются доступный gateway и проверка оператором.
