# Смена IP VPS: входящий адрес и выход в интернет

Подключение SSH по новому адресу не доказывает, что VPS и клиенты Amnezia выходят в интернет через него. Провайдер может добавить второй IPv4 на тот же интерфейс, сохранив старый. При отсутствии явного выбора исходного адреса Linux может продолжить использовать прежний. Docker NAT/MASQUERADE и уже установленные NAT-соединения также требуют отдельной проверки. Страна по стороннему сервису и HTTP 200 от Gemini не подтверждают региональную доступность приложения.

## Что проверяет GoVPN 6.71

Общая проверка **3 → 1** остается только читающей:

- Выбранный интерфейс и исходный IPv4 для маршрута к 1.1.1.1 через JSON iproute2.
- Публичные IPv4, назначенные этому интерфейсу. IPv6, loopback, private и multicast не считаются вторым публичным IPv4.
- Фактический внешний IPv4 ответа HTTPS Cloudflare без proxy из окружения или curlrc.
- Серверный IPv4 текущего SSH из `SSH_CONNECTION`, если значение доступно и имеет корректный формат. Клиентский адрес SSH не выводится. После sudo, через консоль или промежуточный узел подсказка может отсутствовать или обозначать другой участок подключения.

Предупреждение появляется при нескольких публичных IPv4, несовпадении SSH и внешнего выхода либо отличии внешнего IP от публичного исходного адреса проверенного маршрута. Это повод сопоставить настройки с ожидаемым выходом, а не доказательство поломки: несколько IP, NAT, туннель и разные маршруты могут быть намеренными. При сохранении обоих IP предупреждение о нескольких адресах останется и после исправления, чтобы неоднозначный выбор был виден.

GoVPN не знает, какой IP провайдер назвал новым, и не использует SSH-подсказку как целевую настройку. Запрос к Cloudflare и маршрут к 1.1.1.1 могут проходить по разным путям. Недоступные, поврежденные или слишком большие JSON данные не считаются успешной сверкой. Сырые ответы команд и сетевые конфиги в отчет не выводятся. Дополнительные локальные чтения ограничены 7 секундами каждое; новых внешних запросов эта проверка не добавляет.

## Проверка после смены адреса

На VPS сравните назначенные IPv4, исходный адрес маршрута и свежий внешний ответ:

```bash
ip -4 -br address
ip -4 route get 1.1.1.1
curl -q -4 --noproxy '*' --connect-timeout 5 --max-time 10 https://api.ipify.org
```

На устройстве выберите в GoVPN выход **VPS**, переподключите Amnezia и откройте [api.ipify.org](https://api.ipify.org). Ожидаемый адрес уточните в панели/поддержке провайдера. Проверка VPS не заменяет этот шаг: клиентский трафик проходит через Docker и NAT. Затем заново откройте Gemini с тем же аккаунтом. Проверка IPv6 проводится отдельно; отсутствие второго публичного IPv4 не означает отсутствие IPv6 или утечек на устройстве.

Если смена выхода помогает, это подтверждает пользу смены IP в конкретной проверке, но не раскрывает внутреннюю причину отказа Google. WARP для рабочего прямого выхода не требуется.

## Исправление и сохранение

Автоматического выбора адреса и записи в сеть нет, в том числе в «действиях исправления». Нельзя безопасно выбирать первый, последний или адрес SSH без знания схемы сервера. Смена IP может быть дополнительным адресом, переносом, NAT или отдельной услугой. Ответственность провайдера зависит от того, была обещана полная замена или только выдача нового адреса.

Перед изменением нужны backup и проверка нового исходящего адреса с отдельным привязанным HTTPS-запросом. Для renderer networkd Netplan поддерживает `routes[].from`: это исходный адрес маршрута, а не `routing-policy[].from`, который задает условие правила. Вручную редактируют исходный YAML в `/etc/netplan`, а не сгенерированный файл `/run/systemd/network`.

Изменение preferred source VPS не считается исправлением Docker MASQUERADE. Если нужна явная подмена источника клиентского трафика, правило SNAT ограничивают нужной подсетью и выходным интерфейсом, проверяют новым клиентским соединением и сохраняют отдельно. Удалять чужие цепочки, сохранять все динамические Docker-правила как статический firewall, очищать conntrack или перезапускать сеть для диагностики не следует. Не удаляйте старый IP до проверки нового SSH-доступа и зависимых подключений.

`netplan generate` проверяет/генерирует конфигурацию, но не применяет ее к работающей сети. `netplan apply`, перезагрузка и перезапуск Docker - отдельные действия. Проверка синтаксиса или запущенный oneshot unit не доказывают сохранение рабочего пути после реальной перезагрузки; это проверяется отдельно с доступом к консоли провайдера.

Документация: [Netplan routes/from](https://netplan.readthedocs.io/en/stable/netplan-yaml/), [ip route/src](https://man7.org/linux/man-pages/man8/ip-route.8.html), [SNAT и MASQUERADE](https://man7.org/linux/man-pages/man8/iptables-extensions.8.html).
